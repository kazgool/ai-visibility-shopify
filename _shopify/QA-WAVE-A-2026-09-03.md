# Wave A QA: two independent rounds, adjudicated

3 September 2026. Wave A is the port of WordPress 1.7.8's withdrawal behaviour:
products that leave the published state stop appearing in the mirror, in
llms.txt and in anything else put in front of an AI crawler, plus two merchant
toggles (include out of stock, include unlisted).

## What QA found, and what it costs

Marius decides what is committed and when. This section states the findings and
their cost so that decision has the facts; it is not a verdict.

Four items are unmet against the spec: two acceptance rows in PRD I.6, the rule
in PRD I.2, and PRD I.3 which is unamended. Separately,
`reconcileMirrors` can empty a shop's entire mirror on a read that parses to
zero eligible products.

The cost of shipping each as it stands:

| Item | If committed as it stands |
|---|---|
| No floor on the wipe | one field missing from the JSONL empties every shop's public pages, reported as success, with nothing to re-queue |
| Withdrawal gated on the sweep | a lapsed shop keeps every lost-webhook page indefinitely; PRD I.2 says it never should |
| Card counts a different set than llms.txt | the wave's own by-hand check fails on any shop with pre-migration rows |
| PRD I.3 unamended | the spec and the code disagree in writing, so the next reader trusts the wrong one |

All four are small: under half a day together, by the overseer's estimate.
The recommendation is to fix the first three and get the amendment approved
before commit, but that is a recommendation.

## How this was produced

An overseer wrote the QA plan first: the acceptance criteria quoted from PRD
sections I and J, the risk surface, and two briefs on deliberately different
axes so that a defect one reviewer misses is one the other catches. Round 1
read the code closely. Round 2 followed one product from a Shopify state change
to what a crawler receives. Neither saw the other's brief or output. The same
overseer then adjudicated both.

Between the rounds and the adjudication, six load-bearing claims were checked
against source or against shopify.dev by hand. One of the three proposed
ship-blockers did not survive that check (below). The suite was run: 40 files,
485 tests, green, and green with `.env` renamed away.

## Blocking, before commit

**1. The whole-mirror wipe has no floor.**
`app/services/mirror-reconcile.server.ts:102-106`. When `handles` is empty both
arms of the ternary delete every row for the shop, and `complete` is computed
from the root count alone, so a read that parses to zero eligible products with
the right root count reports success and empties the public set. One field that
stops arriving in the JSONL - `status`, `handle`, `onlineStoreUrl` - is enough.
Fix: before the delete, if `read.read.root > 0 && handles.length === 0`, set
`skipped`, log "N products read, none eligible, nothing deleted", return. Root 0
stays a legitimate wipe, which is I.6 row 7.
Blocking because it is the unrecoverable direction the module's own header
names, and because nothing re-queues afterwards: nothing is eligible.

**2. Withdrawal is gated, and the comment that says otherwise is false.**
`worker/tasks.ts:404` returns before `reconcileMirrors` at `:425`;
`reconcile_mirrors` is gated at `:496` with a comment claiming "the weekly sweep
still take a page down on any shop - so refusing here delays a bulk withdrawal,
it does not prevent one". The sweep is gated at `:404`, so it does prevent one.
A lapsed shop keeps every lost-webhook page for ever.
Fix: in `sweep_missing`, reconcile for every installed shop and apply
`mayProcessAutomatically` only to the missing-attributes half; drop the gate in
`reconcile_mirrors` (the POST already gates on paid, and every job the reconcile
queues is gated inside `extract_product`). Rewrite the comment.
Blocking because PRD I.2 states withdrawal is never gated, and this is the
second pass at the same class.
Cost to state to Marius: one bulk export per lapsed shop per week.

**3. The Report count fails I.6's "Second render" row.**
`app/routes/app.report.tsx:246-250` counts `productId: { not: null }`; the
acceptance row is `count(*)` with no clause, and `llms-txt.server.ts:142` lists
every row. The comment above the count claims the two "can never disagree".
Fix: drop the clause, rewrite the comment.
Blocking because the wave's own by-hand check fails on any shop with
pre-migration rows until its first reconcile adopts them.

**4. PRD I.3 is unamended.**
The code computes `complete` from the root count; PRD I.3 change 1 specifies
both counts. The deviation is argued in the CHANGELOG and in code comments,
which CLAUDE.md's Workflow section forbids: an acceptance criterion that is not
met is a failed wave until the PRD is amended and the amendment approved.
Amendment text below, for approval.

## Fix in this wave, not blocking

1. An emptied collection keeps its old `table` metafield and its links to
   products that are now drafts. `collections.server.ts:261` skips the write
   when the table has no columns; nothing withdraws the previous value. PRD I.5
   promises this fix, so the wave is not done without it.
2. `extract.server.ts:499` returns before `dropStaleMirror` at `:510`, so a
   paying shop keeps the page of a deleted product until the weekly sweep while
   a free shop loses it in a minute. Entitlement inverted.
3. The pass writes a mirror row only inside the
   `facts.length > 0 || hasWithdrawableAutoValues` guard, so the reconcile then
   enqueues one `extract_product` per zero-facts eligible product after every
   Fill catalogue. Move the `cacheMirror` call out of that guard.
4. The toggle POST passes no `jobKey` and has no already-running check, while
   every enqueue in `worker/tasks.ts` passes one. Two POSTs ten seconds apart
   produce two JobRuns, two jobs and a bulk-operation collision.
5. A queued `reconcile` row blocks every dashboard button (`app._index.tsx:201`
   is kind-agnostic) and `reconcile` is absent from the stall-detector
   candidates, so with the worker down the lockout is unexplained.
6. A failed or refused reconcile renders no sentence on the card.
7. Handle reuse between two renamed products leaves a row serving one product's
   text under another's URL, reported as a clean pass.
8. The free-tier Products screen tells an unlisted product's owner "Not
   published to the Online Store", which is the one cause it is not.
9. Copy: "1 product pages served" does not pluralise; `app.report.tsx:574`
   states a rule narrower than the one applied.
10. No test covers the `products/delete` handler, `savePrefs`, the report
    action, or the mirror's "availability: out of stock" line.

## Deliberately left, with the reason

- **The bulk-pass snapshot race.** A product unpublished after the export
  started is re-created from the snapshot, and the reconcile preserves it
  because it is handed the same read. The window is one pass and the weekly
  sweep closes it; the cheap fix re-queues the whole catalogue the pass just
  wrote, which is the loop the poll cursor exists to prevent. Record the window
  in PRD I.4; Marius decides.
- **The refusal string on a lapsed shop is unreachable.** That screen shows the
  subscription prompt, which is the right sentence. The reason survives in the
  JobRun report.
- **The Prisma stub reimplements `notIn`.** Acceptable for a unit test whose
  subject is the summary arithmetic; the by-hand rows exercise the real
  predicate.
- **A free slot spent on an unlisted product.** Metafields are written and
  render on the product's own page, which is what "processed" promises. Fix 8
  tells the merchant why there is no text page.
- **Unchecked fetch status and mid-line truncation.** Both throw, the job is
  marked failed, nothing is deleted. Fails closed; the only loss is the card
  saying "failed" rather than "short".

## Wrong or overstated in the two rounds

Recorded because two adversarial rounds that produce nothing wrong have not
been read critically.

- **Round 1: `status:active,unlisted` is invalid Shopify syntax.** Wrong, and it
  was one of the three proposed ship-blockers. shopify.dev's products query
  `status` filter reads "Filter by a comma-separated list of statuses", valid
  values `active`, `archived`, `draft`, `unlisted`, example `status:active,draft`.
  Round 1 reasoned from the generic search-syntax page and never opened the
  filter-specific one. Checked by hand before the adjudication.
- **Round 1: two concurrent exports parse each other's file.** Shopify refuses a
  second bulk query per shop with a userError, which the code throws on. The
  window is one operation completing inside a single poll interval, and the
  second reconcile converges. Worth a one-line id check; not data loss.
- **Round 1: `tablePrefs` is dead code.** PRD I.5 states the out-of-stock toggle
  is deliberately ignored for tables because Shopify's own collection page lists
  sold-out products. Redundant, not wrong.
- **Round 1: truncation throws "rather than reporting incomplete".** Throwing is
  the safe outcome.
- **Round 2: five fixed queries read a broader set.** All five are `first: 1`
  samples used to obtain one product URL for a fetch or an embed check. Nothing
  is published from them, so PRD J.4 does not apply.
- **Round 2: the zero-facts row is never refreshed.** It is refreshed by
  `products/update` and by the poll; only the bulk pass skips it. The real
  defect is the job storm.
- **Round 2: the dashboard lockout never clears.** It clears when the job
  finishes or fails; it is permanent only with the worker down. The missing
  stall entry stands.

## PRD amendment, for approval

To be added to PRD-PORT-1.7.8.md section I.3, after the `CatalogueRead` block:

> **Amendment, 3 September 2026.** `complete` is `expected.root === read.root`
> only. The object count does not vote. Reason: the only decision `complete`
> protects is a delete, and a delete is made from the set of product handles; a
> short download always shows as fewer root products parsed than
> `rootObjectCount` announced. `objectCount` is a different measure - Shopify
> counts child rows, this parser counts non-empty JSONL lines - and if the two
> definitions ever differ by one, requiring both would make `complete` false on
> every shop and the withdrawal inert while appearing to ship. The object
> comparison is kept as `objectsMatch: boolean` on `CatalogueRead`, written into
> the JobRun report and the log line, and read by nobody as a veto. The type is
> therefore `{ products, complete, objectsMatch, expected, read }`. Approving
> this amendment accepts that a download truncated in a way that keeps the root
> count intact (none is known) would not be caught by this flag; the
> eligible-set floor in `reconcileMirrors` is the second guard.
