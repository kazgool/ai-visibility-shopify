## Gaps

Ranked by severity, worst first.

1. **Medium - SEO apply re-fetches the product but never re-checks `eligibility()` against the merchant's current toggles at write time (row 10, `seo-bulk.server.ts` `runSeoApply`, around line 180).** `writeSeo` will happily set `seo.title`/`seo.description` on a product that has gone from eligible to draft/archived/unlisted-excluded between queue build and apply - the SEO fields are stored on Shopify's own Product object either way, so this is not a false public claim (unlike the mirror row), but it is a write the app makes to a product a merchant just took off the storefront. Smallest fix: in `runSeoApply`'s per-product loop (`seo-bulk.server.ts` ~line 178-193), call `eligibility(fresh, prefs)` and skip (report as skipped, not written) when not eligible. The same applies to `runCollectionSeoApply` for collections that lost `published_status:published` between build and apply.

2. **Low - `app.products.$id.tsx` capsule save (row 13) and alt save (row 14) have no explicit "value unchanged" short-circuit before calling `metafieldsSet`/`productUpdateMedia`.** Because these are interactive, single-product, human-initiated saves (the merchant clicked Save), the risk is much smaller than a bulk pass - at most one extra write per click, not a feedback loop - but it is still a write that could be skipped when the form re-submits the same value. Smallest fix: compare against `origSummary`/`origFitFor`/`origQuestions` (already read into the action, e.g. `app.products.$id.tsx` around line 559-561) before pushing, which the code already does for state provenance but not as a full no-op skip for the metafieldsSet call itself when every field is unchanged.

3. **Low - `app.business.tsx` business-info save (row 21) has no G3 (entitlement) check and no G4 (identical-value) guard.** A shop with no paid access can still save business info, which then feeds `capsuleFields` used in row 1/3's writes (which *are* gated). So this is not itself a leak of gated content, but it is inconsistent with the rest of the app's "re-check entitlement at every write" rule. Smallest fix: none required for correctness (the downstream write is what matters and is gated); note only.

4. **Low - `webhooks.themes.publish.tsx` (part of row 22) has no `mayProcessAutomatically` check before writing the shop `theme_scan` metafield**, unlike `seo_watch`'s scheduled version of the same write. Since this metafield is diagnostic (drives whether the storefront block emits or extends structured data) rather than merchant-visible published content, and the write happens once per theme publish event (not a loop), the blast radius is small, but it is the one webhook-triggered write in the app with zero entitlement check. Smallest fix: add `mayProcessAutomatically`/`mayProcessAutomaticallyCached` check at the top of the action, mirroring `extract_product`'s webhook-side backstop (row 1).

5. **Unverifiable/low - the storefront Liquid extension (row 23) was not read line-by-line** (extensions/ are out of scope per the audit's "no build" constraint, and Liquid isn't greppable the same way); if it renders `product.metafields['$app'].facts` etc. directly without checking `product.available`/`product.tags` or similar, a product that is `ACTIVE` but excluded by the merchant's out-of-stock toggle would still show the extension's own content on its own page - but that is arguably correct, since the toggle governs *public mirror/llms.txt/collection* visibility, not the product's own page, and Shopify itself would not render a draft product's page at all. Flagged for the reviewer to confirm this is intentional (see Not gaps #1 logic) rather than assumed.

## Not gaps

1. **G1 is intentionally `no` for the metafields write itself in `writeFacts`/`writeVariantFacts` (rows 1-2).** Documented directly in `extract.server.ts` (comment above line 543) and `facts.server.ts`: facts/summary/questions/fit_for are written to the product's own metafields regardless of eligibility, because "its metafields are still written, because its own product page renders them wherever Shopify renders it." Eligibility only gates the *public mirror page* (row 3/4) and the *comparison table/collections* (row 7), which are surfaces this app creates beyond the product's own page. This is the same design the collections fix (row 7-8) extended to collections themselves.

2. **G5 is `n/a` for alt text (row 5).** Alt text is never "withdrawn" to empty the way facts/summary are, because there is no equivalent of "the engine no longer finds anything" for alt text - the alternative to writing new alt text is leaving the existing (human or previously machine) text in place, which is the correct behavior for an accessibility attribute; deleting it would leave images with no alt text at all, which is worse than a stale one.

3. **G5 is `n/a` for SEO title/description (rows 9-11).** Unlike facts, an SEO title/description is never allowed to go empty by design - `writeSeo`/`writeCollectionSeo` only ever propose a replacement value, never blank. The correct "undo" mechanism is `revertSeo`/row 12, an explicit merchant action, not an automatic empty-branch withdrawal.

4. **G3 is intentionally `no` for the reconciliation/withdrawal half of `sweep_missing`/`reconcile_mirrors` (row 15) and `dropStaleMirror` (row 16).** This is the explicit, documented rule stated in `worker/tasks.ts` comments at both call sites: "withdrawal is never gated" (PRD-PORT-1.7.8 I.2). Taking a page down writes nothing to Shopify and costs nothing the free tier is meant to withhold; only *queueing new writes* for a lapsed shop is gated. This is the correct shape per the `enforce-entitlement-gates` rule ("a gate withholds new work, it does not take back what was granted, and withdrawal is not new work").

5. **G3 is `n/a` for the proxy's serve-time read (row 17) and llms.txt generation (row 18).** These read pre-written, pre-gated data; re-checking entitlement on every public HTTP request would mean an Admin API call per storefront/crawler hit, which the architecture explicitly avoids (PRD §5.2, "no Admin API on the request path"). The correct enforcement point is at write time (rows 3/4/7), which is where it is applied.
