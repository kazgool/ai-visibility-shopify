Method: read-only trace of app code (no npm install / vitest / build run, per instructions). Every file path below is `app/...` or `worker/...` relative to the repo root `ai-visibility-shopify`.

### I1 "Nothing a human wrote is ever overwritten."

**Attack log**

1. Tried: find every metafield writer that skips the `state`/`mayWrite` guard. Grep `metafieldsSet\|productUpdateMedia` across `app/services`. Result: writers are `facts.server.ts` (`writeFacts`, `writeVariantFacts`), `alt-text.server.ts` (`writeAltText`), `collections.server.ts` (`writeCollections`), `seo.server.ts` (SEO title/description, via `mayWriteSeo`), `business.server.ts` / `billing.server.ts` (shop-level metafields, not merchant content). All merchant-content writers route through a `mayWrite`/`mayWriteSeo` function. Result: guarded.
2. Tried: value exists with NO `state` entry (pre-install value, another app, hand-set before install) - is it treated as human? Traced `mayWrite` at `app/services/facts.server.ts:113-121`: `if (existing && existing !== "" && !entry) return false;` - an unexplained non-empty value blocks the write. Same pattern in `collections.server.ts:159-163` and `seo.server.ts:71-79` (`mayWriteSeo`). Result: guarded, correctly defaults to "treat as human."
3. Tried: state metafield fails to parse (corrupt JSON). Traced `parseState` in `facts.server.ts:82-89`: `catch { return {}; }` - empty state means every existing non-empty value is then judged by rule 2 above (blocks the write). Only a product whose state failed to parse AND whose field is also empty would be treated as writable. Result: guarded - fails closed toward "protect", not toward "overwrite".
4. Tried: reinstall with old metafields present. The write path only ever reads `product.metafields` fetched fresh each pass (`facts.server.ts`, `collections.server.ts` do not cache); a reinstalled shop's old `$app.facts` / `$app.state` metafields survive in Shopify (metafields are not app data, they persist) and are read exactly as any other pass would read them. Result: guarded by the same generic mechanism, could not find a reinstall-specific bypass.
5. Tried: per-product editor (`app/routes/app.products.$id.tsx`) marking a field human on manual edit, and whether a later bulk pass honours it. Traced lines 580-643: editing summary/fit_for/questions/facts sets `state.<key> = { source: "human", ... }` before the metafieldsSet call. `writeFacts`'s `mayWrite` (facts.server.ts:113) reads exactly this state entry on the next bulk pass and refuses to touch it. Result: guarded, traced end to end.
6. Tried: alt text - does the writer check `state` the way `facts.server.ts` does, or does it use a content heuristic instead? Traced `writeAltText` in `alt-text.server.ts:107-115`: the ONLY guard against overwriting a human-written alt is `existing !== "" && !looksLikeMachineAlt(existing)`. There is no read of the product's `state` metafield's `alt_text` entry to decide whether the *existing text* is human before overwriting; `state` is only written *after* a decision to overwrite has already been made (to log which media got a timestamp), never consulted before. Result: **this is structurally different from every other writer** - it substitutes a content heuristic for the state-based guard the rest of the app uses.
7. Tried: construct a human-written alt text that `looksLikeMachineAlt` misclassifies as machine-written, to prove attempt 6 is exploitable, not just architecturally unusual. Traced `looksLikeMachineAlt` in `app/engine/alt-text.ts:64-84` via `looksLikeFilename` (lines 44-52): a single-token alt text matching `/^\d{8,}$/` (8+ digits, no other content) is judged a filename and therefore "machine". A merchant who types a product code as alt text, e.g. alt = `"20260527"` (their own SKU, entered by hand because that's what they had), is a real, deliberate human entry that satisfies this pattern. Also: `/^[a-f0-9]{8,}$/i` (line 26 in FILENAME_PATTERNS) matches any single hex-looking word of length >= 8, so a merchant who types a hex-ish product code (e.g. `"a1b2c3d4"`) by hand is also caught. Result: **violation confirmed** - see below.

**Verdict:** VIOLATED (alt text only; facts/collections/SEO title-description HOLD, guarded as in attempts 1-5, file:line cited above).

**Violations**

1. `app/services/alt-text.server.ts:107-115` (guard), backed by `app/engine/alt-text.ts:44-52,64-84` (heuristic).
   Sequence:
   1. Merchant manually types alt text for a product photo in Shopify admin, entering their own product code as the description, e.g. `"20260527"` or `"a1b2c3d4"` (plausible: many merchants alt-tag with an internal SKU rather than a description).
   2. `bulk_alt_text` (or `extract_product`'s alt-text step) runs for this product.
   3. `alt-text.server.ts:109` evaluates `existing !== "" && !looksLikeMachineAlt(existing)`. `looksLikeMachineAlt("20260527")` returns `true` via `looksLikeFilename` (`^\d{8,}$`), so the human-protection branch (line 108-116, `outcome.keptHuman += 1; return;`) is skipped.
   4. The generated alt text (`buildAltText(...)`) overwrites the merchant's own text, because there is no check of `state.alt_text.source === "human"` anywhere in this function - the only thing ever consulted is the live string's shape.
   What the merchant sees: their own hand-typed alt text on that image silently replaced by the app's generated sentence, with no warning, the next time any alt-text pass runs - the same failure mode CLAUDE.md I1 exists to prevent, just reached through a text heuristic instead of a missing state-metafield check.
   Smallest fix: before the heuristic check, read the product's `state` metafield's `alt_text.source`; if `human`, never touch that image (matching the pattern every other writer already uses), and only fall back to `looksLikeMachineAlt` for images that have no recorded state at all (first-run detection of pre-existing filename junk).

### I2 "A draft, archived or unlisted product never reaches an AI surface."

**Attack log**

1. Tried: trace every caller of `eligibility()`. Grep across `app`/`worker` (excluding tests/definition file): `collections.server.ts:206`, `extract.server.ts:245,461,543`, `mirror-reconcile.server.ts:85`. Result: four call sites, all read.
2. Tried: ACTIVE-to-DRAFT transition - does every surface withdraw? Traced `extract_product` (worker/tasks.ts:184-208): on a gate failure it calls `withdrawIfIneligible` (line 200) which is documented (lines 189-199) as unconditional regardless of entitlement - "Withdrawal is never gated". On a gate pass it calls `extractOneProduct`, which per `extract.server.ts:461,543` re-checks `eligibility()` and, per the file's own comments (not independently re-read in full here, flagged below), withdraws a no-longer-eligible product's mirror row. `mirror-reconcile.server.ts:85` (`reconcileMirrors`) is the sweep-style backstop: it builds an eligible-handle map from a *complete* bulk read and deletes any MirrorCache row not in that map (line ~90-110, "the single delete statement... is the whole fix"), explicitly covering "unpublished, drafted, archived, deleted, renamed, excluded by toggle." Result: guarded, three independent layers (per-product write path, extract_product withdrawal-on-refusal, weekly reconcile sweep).
3. Tried: product deleted in Shopify - does `products/delete` clear MirrorCache so llms.txt drops it? Read `app/routes/webhooks.products.delete.tsx:14-27`: deletes `db.mirrorCache` rows by reconstructed GID, and also `db.seoScan` rows. Result: guarded, file:line above.
4. Tried: llms.txt/agents.md read path - does it filter by product status at request time, or trust MirrorCache fully? Traced `llms-txt.server.ts:209-220`: reads `db.mirrorCache.findMany({ where: { shopId } })` with no additional eligibility check - by design (comment at `mirror-reconcile.server.ts:6-9`, "no Admin API on a public request... so a row that should not exist is two leaks at once"). This makes MirrorCache the single source of truth for I2 on the whole proxy surface, which puts all the weight on the writers/reconcilers (attempts 2-3). Since those are guarded, this is not an independent hole, but it is a single point of failure: any writer that adds a MirrorCache row without checking `eligibility()` bypasses I2 for every surface at once. Result: could not find such a writer (`extract.server.ts` is the only writer of MirrorCache rows found in this pass - not fully read line by line here; flagged as unverified below).
5. Tried: a truncated/partial bulk catalogue read during `reconcileMirrors` - does it delete indiscriminately (false eligibility) or refuse to act? Traced lines 68-79: `if (!read.complete) { summary.skipped = true; ...return; }` - explicitly refuses to delete on a short read. Result: guarded, fails toward leaving stale pages up for a week rather than mass-deleting; correct direction for I2 (a false negative here is not an I2 violation, since nothing new is added to any surface - it is a staleness issue, not an eligibility bypass).
6. Tried: collection tables - do rows link to ineligible members? Traced `eligibleMembers` (`collections.server.ts:191-203`), which calls `eligibility()` per member with out-of-stock forced included (matching Shopify's own collection page behaviour) and unlisted honoring the toggle. Result: guarded.

**Verdict:** HOLDS, on the paths traced (file:line above). One item not independently re-verified end to end: whether `extract.server.ts`'s `extractOneProduct` MirrorCache write at line 461/543 is the *only* MirrorCache writer in the codebase (attempt 4) - I grepped for `eligibility(` callers but did not grep separately for every `mirrorCache.create`/`upsert` call site. Labelled a suspicion, not a finding.

**Violations:** none found and confirmed.

### I3 "The free tier is exactly the crawler check and three merchant-chosen products; paid features never run for a free shop."

**Attack log**

1. Tried: grep `mayProcessAutomatically\|mayProcessAutomaticallyCached` across every worker task. Result (worker/tasks.ts): `bulk_extract` (line 112), `extract_product` (line 190, cached form), `bulk_alt_text` (line 371), `bulk_collections` (line 650... actually the entitlement check at line ~1293 for `bulk_collections`, confirmed by direct read), `scanProductPagesForShop`/`seo_scan_products` (line 1052), `seo_collection_apply`/`seo_apply` route through `runCollectionSeoApply`/`runSeoApply` (not independently re-read; see below), `crawler_check` (no gate found - and none is required, since the crawler check IS the free-tier feature per FREE-TIER-SPEC). 2. Tried: read `bulk_extract` (worker/tasks.ts:85-163) end to end for the historical "three background jobs bypassed the cap" bug. Found the gate at line 112, inside the try block, with an explicit comment explaining it is deliberately re-checked at execution time, not only at enqueue, and explaining why it is inside the try (an API throw must not strand the JobRun at "queued"). Result: guarded, and the code comments show this was a deliberate fix for a documented past incident (matches CLAUDE.md history), not new territory.
3. Tried: `bulk_collections` (worker/tasks.ts:1279-1310) - the exact task named in the brief's known violation (2,491 collections). 4. Tried: webhook `products/update` for a free shop - does it enqueue extraction for a 4th (non-free) product? Traced `app/routes/webhooks.products.update.tsx:1-24`: unconditionally enqueues `extract_product` for any product GID, with no free-tier check at the route level. The gate is entirely downstream, in `extract_product` itself via `mayProcessAutomaticallyCached` (worker/tasks.ts:190). Traced that function (billing.server.ts, `mayProcessAutomaticallyCached`): `if (await isComped(...)) return true; return shop.plan !== "none";` - a free shop's `Shop.plan` column is `"none"` (per `recordPlan`, called on subscription changes), so this correctly refuses. Result: guarded, but entirely by a single downstream check with a documented staleness trap (the function's own comment: `Shop.plan` is refreshed only when the merchant opens the app, so a shop that cancels and never returns keeps reading its last-seen plan "forever" until the next `poll_changes`/`sweep_missing` catches it with the live, authoritative check). Result: labelled a suspicion / accepted-design ambiguity, not a clean violation - the code and its comments are consistent with each other; the CLAUDE.md invariant as I was given it ("paid features never run for a free shop") is stricter than what the code's own comments claim it guarantees.
5. Tried: does a free shop's 4th manually-chosen product get processed by the per-product route (not automatic)? Did not locate and read the specific route action that calls `addFreeProduct`/checks the cap for a manual single-product extraction request (e.g. `app/routes/app.products._index.tsx`, referenced in `billing.server.ts`'s comment on `addFreeProduct`) in this pass. Result: **could not determine** - not traced.
6. Tried: SEO unlock and collections/alt-text for a free (non-SEO-unlocked, non-paid) shop via the manual "process this product" action in the product editor. Not traced in this pass due to time. Result: **could not determine**.

### I4 "The app never feeds itself."

**Attack log**

1. Tried: every metafieldsSet writer for an identical-value check. Traced `facts.server.ts:262-269` (`if (current === field.value) { unchanged; continue; }`), `collections.server.ts` (same pattern, "Never write an identical value" comment), `alt-text.server.ts:139-146` (`if (alt === existing) return;`), `seo.server.ts:194-199` (same). Result: every writer found has the check, guarded.
2. Tried: does the identical check compare against a stale in-memory copy rather than the freshly fetched value? Traced `writeFacts`: `product.metafields` is the argument passed in by the caller for this one pass - i.e. whatever `extract.server.ts` fetched immediately before calling `writeFacts`. Did not independently verify that `extract.server.ts`'s fetch is always the most recent state (e.g., not a value cached from an earlier stage of a multi-step pipeline). Result: **could not determine** without reading `extract.server.ts` end to end (partially read via grep only).
3. Tried: does `metafieldsDelete` (withdrawal of a stale auto fact) fire a webhook that re-creates the value? Traced `facts.server.ts:238-248`: a deletion only happens when the newly computed value is empty AND the existing state says `source: auto`. The deletion removes the metafield and drops the `state[field.key]` entry (line 244, `delete state[field.key]`) before the state metafield itself is rewritten. A `products/update` fired by this delete would re-enqueue `extract_product`, which recomputes facts; if the description still yields nothing, the same "empty, existing gone, no-op" path is hit and nothing is deleted again (deletion is a no-op once the metafield is already gone: `if (existing && existing !== "" ...)` at line 240 requires `existing` truthy from the product's own metafields, which would no longer include the deleted key on the next fetch). Result: guarded against re-triggering deletes, self-terminates after one cycle.
4. Tried: can a pass that changes nothing still rewrite the `state` metafield, and loop? Traced `writeFacts`: `touched` is only set `true` inside the "written" branch (line 268) or the "removed" branch (line 246) - the "unchanged" branch (line 263-266) does not set `touched`. The final `if (touched) { metafields.push(...state...) }` (line ~280) means a fully-unchanged pass pushes zero metafields, including no `state` write. Result: guarded - confirmed by direct read, file:line above.
5. Tried: same question for `alt-text.server.ts`'s state stamp. Traced lines 148-175: the `state` (SET_STATE) mutation only runs inside `if (updates.length > 0)` (line 148), i.e. only after at least one real, non-identical media update was already sent. 6. Tried: variant facts (`writeVariantFacts`, facts.server.ts:330-370) for the same three guards. Traced: human-state check (line ~355), unexplained-value check (line ~356), identical-value check (line ~360, `if (existing === value) continue;`). Result: guarded, same shape as product facts.

**Verdict:** HOLDS on every writer traced (file:line above). One item **could not determine** (item 2 - whether `extract.server.ts`'s product snapshot passed into `writeFacts` could ever be stale relative to the live metafield, e.g. across two products' writes sharing one fetch) - not read in full this pass.

### I5 "The request path never calls the Admin API and never does heavy work."

**Attack log**

1. Tried: read `app/routes/proxy.$.tsx` in full (175 lines) for any Admin GraphQL call. Result: none. Every read is `db.setting.findUnique`, `db.shop.findUnique`, `db.mirrorCache.findUnique`, or (for llms.txt) `llmsTxtBody`. `authenticate.public.appProxy(request)` verifies the proxy HMAC signature only, no Admin API round trip. Result: guarded for the Admin-API half of I5.
2. Tried: trace `llmsTxtBody`'s transitive DB calls for unbounded queries. Traced `llms-txt.server.ts:209-220`: `db.mirrorCache.findMany({ where: { shopId }, select: { body, handle }, orderBy: { handle: "asc" } })` - **no `take`/`limit` clause**. MirrorCache grows one row per eligible product, so on a store with, say, 20,000 products this loads all 20,000 mirror bodies (full text page content, not just handles) into memory on every single request to `/apps/.../llms.txt`, which is public and cacheable but still hits the app server on a cache miss / for any crawler that doesn't respect `Cache-Control: max-age=300`. Result: **violation confirmed**.
3. Tried: same check for the per-product mirror path (line ~150-166 of proxy.$.tsx). Uses `db.mirrorCache.findUnique({ where: { shopId_handle: ... } })` - single indexed row, bounded. Result: guarded.
4. Tried: `businessFor`, `persistedShopName`, `persistedCollectionsIndex` (the other three `Promise.all` legs in `llmsTxtBody`). `businessFor`/`persistedShopName` are `db.setting.findUnique` (indexed, bounded). `persistedCollectionsIndex` (llms-txt.server.ts, around line 190) parses a single Setting row's JSON value (an already-bounded, precomputed index written by `bulk_collections`), not a live `findMany` over the Collection table. Result: guarded, only the MirrorCache read (item 2) is unbounded.
5. Tried: any per-request extraction or heavy computation (e.g. re-running the engine, re-fetching from Shopify) on the proxy path. Traced: `llmsTxtBody` only reads precomputed `MirrorCache.body` strings and renders them with `renderLlmsTxt` (string templating, no engine calls). Result: guarded - no per-request extraction found.

**Verdict:** VIOLATED (one finding; everything else on the traced path HOLDS, file:line above).

**Violations**

1. `app/services/llms-txt.server.ts:212-217` (the `db.mirrorCache.findMany` call, no `take`), reached from `app/routes/proxy.$.tsx:141-145` (the `llms.txt`/`agents.md` branch) on every uncached proxy request.
   Sequence:
   1. A merchant catalogue grows into the thousands of eligible products (a real, expected end state for a growing store, not a hostile input).
   2. Any request to `https://<store>/apps/ai-visibility/llms.txt` or `.../agents.md` that misses Shopify's edge cache (past the 5-minute `max-age`, or a crawler that ignores cache headers, which several stated target crawlers - GPTBot, ClaudeBot etc. - are not guaranteed to respect) reaches `proxy.$.tsx`.
   3. `llmsTxtBody` runs `db.mirrorCache.findMany({ where: { shopId } })` with no limit, pulling every mirror row's full `body` text for the shop into Node memory and iterating all of them synchronously (`for (const m of mirrors)`, llms-txt.server.ts:222) before a byte of the response is sent.
   What the merchant would see: on a large catalogue, `agents.md`/`llms.txt` requests get slower and heavier as the catalogue grows, with no cap - directly contradicting "the request path never does heavy work" and threatening storefront performance on the free path any AI crawler hits. This is proportionally the same shape of bug as the 2,491-collections incident (an operation with no upper bound that scales with catalogue size, on an automatic/public path).
   Smallest fix: this function already has to render a bounded llms.txt anyway (a real llms.txt for a 20k-SKU catalogue is not a useful document to any consumer at full length); add a `take` cap (e.g. a few hundred/thousand rows, matching whatever cap `renderLlmsTxt` already imposes on output size, if any) and, if the full index must still be complete, move the full read to a precomputed cached document refreshed by the worker rather than assembled per request - the same pattern already used for `persistedCollectionsIndex`, which solves exactly this problem for collections.

## Ranked

1. **I5 - unbounded `mirrorCache.findMany` in `llms-txt.server.ts:212-217`, served from `proxy.$.tsx` on every uncached request.** Worst because it is on the public, unauthenticated, per-request storefront path (not a background job), scales with the exact metric the product is proud of (catalogue coverage), and a slow/heavy `llms.txt` is a slow storefront for every visitor sharing that Fly machine, not just the requester.
2. **I1 - `looksLikeMachineAlt` heuristic overwrites human alt text matching a filename-like pattern (`app/engine/alt-text.ts:44-52`, `app/services/alt-text.server.ts:107-115`).** Real but narrower: it only fires when a merchant's genuine hand-typed alt text happens to look like a bare filename/SKU/hex code, and the damage is confined to one field on one image, silently replaced rather than a wider blast radius.
3. **I3 (documented ambiguity, not confirmed) - webhook-driven `extract_product` for a lapsed-but-not-reopened free/expired shop can run once more than the free tier promises, per the code's own comments in `billing.server.ts`.** Ranked last because the code and its own documentation both acknowledge this as intended behaviour ("even then webhook-driven extraction keeps running"), so it may not be a bug at all - flagged for Marius to confirm the invariant's exact wording against this documented exception.
